# Banc de test local — plateforme MHX

Tests automatisés de `index.html` avec Playwright + Chromium. **Supabase est simulé** : aucun appel ne part vers la vraie base, toute écriture est interceptée et journalisée. Les données sont **fictives** (`fixtures.js` : 1 coach « Coach Démo », 3 clients « Thomas / Sarah / Julien Démo ») ; le catalogue vient des fichiers `donnees/` du dépôt. Ce dossier ne contient aucune clé ni aucune donnée client.

## Banc complet en une commande (v52)
```
bash tests-locaux/banc.sh [dossier des journaux]            # toutes les suites l'une après l'autre, puis rig.js et la fonction emails
BANC_CHROME=1 bash tests-locaux/banc.sh                      # sur le Mac, avec le Google Chrome de la machine
BANC_LIBRE=1 bash tests-locaux/banc.sh                       # essai sur des modifications non commitées (le résultat ne vaut pour aucun commit)
```
Environ 35 minutes. Code de sortie 1 au moindre échec : une ligne ✗, un bloc interrompu, un code de sortie non nul, **un nombre de ✓ différent du nombre exact attendu** (`attendu()` dans `banc.sh`, à relever dans le même commit que la suite : une vérification sautée sans le dire, ou ajoutée sans le dire, devient un échec), une suite `verif*.js` ni au banc ni dans `HORS_BANC`, une erreur, une écriture ou une page manquante pendant `rig.js`, un test de la fonction emails raté. Le banc teste `index.html` tel qu'il est sur le disque : il ne conclut « vert » que si aucun fichier suivi n'est modifié et que le commit ne change pas pendant qu'il tourne (le bilan affiche le commit testé). Pour tester un commit pendant qu'on travaille : `git worktree add /tmp/banc <commit>` puis le banc dans ce dossier. Deux bancs peuvent tourner en même temps sur une machine, dans deux copies différentes, avec `BANC_VERROUS=<dossier commun>` : chaque suite a son propre port, et ce verrou empêche seulement la même suite de tourner deux fois à la fois (pas plus de deux bancs sur un MacBook Air).

**GitHub Actions** (`.github/workflows/pages.yml`, « Tests puis publication ») rejoue le banc à chaque push sur `main`, sur une machine où la vraie base Supabase et Brevo sont rendus injoignables (`/etc/hosts`, vérifié avant les tests), et ne publie le site que si tout est vert — **seulement une fois la source de GitHub Pages passée sur « GitHub Actions »** ; avant, GitHub publie chaque push lui-même, sans attendre le banc (le journal le signale par un avertissement). `verif52` y compare les écrans du client avec le commit publié juste avant (`VERIF52_REF`), et non avec `main` (qui serait le commit testé lui-même). Le banc y est découpé en 4 parties parallèles (`BANC_PARTIE=1…4`, liste `partie()` de `banc.sh` : toute suite doit y figurer) : environ 10 à 15 minutes, et la publication attend les 4. Urgence : lancer le workflow à la main avec « urgence » coché publie `main` sans attendre le banc — **uniquement pour revenir en arrière**, jamais pour publier du nouveau code. En cas d'échec, les journaux du banc sont joints au passage (dépôt public : données fictives uniquement).

**Horloge** : `verif36` et `verif38` supposent qu'on est entre vendredi et dimanche (formulaire du bilan proposé). Tous les jours, elles décalent tout — données fictives, simulation et navigateur (`clock.install`) — au samedi 12 h de la semaine, ce qui évite aussi tout passage de minuit pendant la suite. Avant la v52 : verif38 65/67 et verif36 8/13 (5 vérifications sautées) du lundi au jeudi.

## Ajouter un test pour une nouvelle version
Copier `verif37.js` en `verifNN.js`, garder la simulation Supabase telle quelle, ajouter les vérifications de la phase (présence des éléments, écritures attendues sur les bonnes clés `donnees`, aucune écriture inattendue). Enrichir `fixtures.js` si une nouvelle clé apparaît (respecter exactement la forme écrite par `index.html`).

## Sans Chromium Playwright : le Chrome de la machine
Si `npx playwright install chromium` n'a pas été fait, le préchargement `chrome-systeme.js` fait tourner tous les scripts avec Google Chrome installé (canal « chrome »), sans toucher aux tests :
```
NODE_OPTIONS="--require ./chrome-systeme.js" node rig.js --html ../index.html --out captures/v38
```

## Règle d'or des simulations
Chaque script intercepte Supabase et **ne doit jamais laisser partir une requête vers la vraie base**. Router par nom d'hôte (`new URL(u).hostname === "localhost"`, `.endsWith(".supabase.co")`), jamais par sous-chaîne de l'URL : les appels d'authentification portent `redirect_to=http://localhost…` et seraient sinon envoyés à la vraie base (incident du 25/09/2026, sans conséquence : inscriptions refusées par Supabase, aucune donnée créée).
