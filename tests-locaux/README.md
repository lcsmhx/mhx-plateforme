# Banc de test local — plateforme MHX

Tests automatisés de `index.html` avec Playwright + Chromium. **Supabase est simulé** : aucun appel ne part vers la vraie base, toute écriture est interceptée et journalisée. Les données sont **fictives** (`fixtures.js` : 1 coach « Coach Démo », 3 clients « Thomas / Sarah / Julien Démo ») ; le catalogue vient des fichiers `donnees/` du dépôt. Ce dossier ne contient aucune clé ni aucune donnée client.

## Banc complet en une commande (v52)
```
bash tests-locaux/banc.sh [dossier des journaux]            # toutes les suites l'une après l'autre, puis rig.js et niveau-haut.js
BANC_CHROME=1 bash tests-locaux/banc.sh                      # sur le Mac, avec le Google Chrome de la machine
BANC_LIBRE=1 bash tests-locaux/banc.sh                       # essai sur des modifications non commitées (le résultat ne vaut pour aucun commit)
```
Environ 35 minutes. Code de sortie 1 au moindre échec : une ligne ✗, un bloc interrompu, un code de sortie non nul, **un nombre de ✓ différent du nombre exact attendu** (`attendu()` dans `banc.sh`, à relever dans le même commit que la suite : une vérification sautée sans le dire, ou ajoutée sans le dire, devient un échec), une suite `verif*.js` ni au banc ni dans `HORS_BANC`, une erreur, une écriture ou une page manquante pendant `rig.js`. Le banc teste `index.html` tel qu'il est sur le disque : il ne conclut « vert » que si aucun fichier suivi n'est modifié et que le commit ne change pas pendant qu'il tourne (le bilan affiche le commit testé). Pour tester un commit pendant qu'on travaille : `git worktree add /tmp/banc <commit>` puis le banc dans ce dossier. Deux bancs peuvent tourner en même temps sur une machine, dans deux copies différentes, avec `BANC_VERROUS=<dossier commun>` : chaque suite a son propre port, et ce verrou empêche seulement la même suite de tourner deux fois à la fois (pas plus de deux bancs sur un MacBook Air).

**GitHub Actions** (`.github/workflows/pages.yml`, « Tests puis publication ») rejoue le banc à chaque push sur `main`, sur une machine où la vraie base Supabase et Brevo sont rendus injoignables (`/etc/hosts`, vérifié avant les tests), et ne publie le site que si tout est vert — **seulement une fois la source de GitHub Pages passée sur « GitHub Actions »** ; avant, GitHub publie chaque push lui-même, sans attendre le banc (le journal le signale par un avertissement). `verif52` y compare les écrans du client avec le commit publié juste avant (`VERIF52_REF`), et non avec `main` (qui serait le commit testé lui-même). Le banc y est découpé en 4 parties parallèles (`BANC_PARTIE=1…4`, liste `partie()` de `banc.sh` : toute suite doit y figurer) : environ 10 à 15 minutes, et la publication attend les 4. Urgence : lancer le workflow à la main avec « urgence » coché publie `main` sans attendre le banc — **uniquement pour revenir en arrière**, jamais pour publier du nouveau code. En cas d'échec, les journaux du banc sont joints au passage (dépôt public : données fictives uniquement).

**Horloge** : `verif36` et `verif38` supposent qu'on est entre vendredi et dimanche (formulaire du bilan proposé). Tous les jours, elles décalent tout — données fictives, simulation et navigateur (`clock.install`) — au samedi 12 h de la semaine, ce qui évite aussi tout passage de minuit pendant la suite. Avant la v52 : verif38 65/67 et verif36 8/13 (5 vérifications sautées) du lundi au jeudi.

**Fichiers de la page (52.1)** : `index.html` charge `css/` et `js/` (listes `MHX_CSS` / `MHX_JS`, numéro `MHX_FICHIERS` en `?v=`). Chaque suite sert la page **et** ces fichiers depuis le dossier de la page testée, avec les mêmes retouches (`fichiers.js` : `servirFichier(req, res, HTML, retouche)` au début du serveur ; `source(HTML)` pour chercher un texte dans la page et tous ses fichiers, ex. la version ou `CONFIG`). Une nouvelle suite fait de même. `inscription_libre` (ouverte dans `js/config.js` depuis la v54) : les suites qui testent l'inscription (rig, verif39, 40, 50, 52, 53, 55 ; hors banc verif44, 47) la **forcent** dans les deux sens avec `forcerInscription(texte, valeur)` (v55, `fichiers.js`), fermée par défaut et ouverte le temps de leurs blocs d'inscription ; les autres suites servent la valeur du fichier. `valeursInscription(texte)` en donne les valeurs (verif52 : une seule attendue ; `true` n'y est accepté que si le commit qui l'a passé à `true` contient « ouverture de l'inscription » dans son message, `false` passe toujours). `rig.js` vérifie sur chaque page capturée que chaque fichier de `css/` et `js/` est chargé une seule fois avec `?v=<MHX_FICHIERS>`, sans 404, et que `CONFIG.marque.version` finit par ce numéro (sinon erreur `[fichiers]`, banc rouge) ; son rapport garde aussi le relevé brut de la console (`console`) pour comparer deux versions. `niveau-haut.js ../index.html` (sans navigateur, au banc, partie 10) vérifie l'ordre de chargement : chaque fichier `js/` se compile seul, aucun nom déclaré deux fois, et aucun code exécuté au chargement d'un fichier n'utilise un nom d'un fichier chargé plus tard (code de sortie 1 sinon).

## Installation
```
npm install -g playwright            # une fois
npx playwright install chromium      # une fois
export NODE_PATH=$(npm root -g)
```

## Lancer (depuis ce dossier, à la racine du dépôt)
```
node rig.js --html ../index.html --out captures/vNN [--theme light] [--only client|coach|anon] [--lang en]   # v52 lot D : + calculateur, Ma progression et « Mon journal » du prospect (84 pages)
      # ~64 pages (client, coach, fiche client, connexion) en mobile et desktop : captures + erreurs console
node flux.js ../index.html captures/flux   # 19 tests : fenêtres UI (annuler = aucune écriture), thème, anglais
node verif34.js ../index.html              # navigation, accueil, bloc Mes données, alias (13)
node verif35.js ../index.html              # programme, nutrition, suivi, progression (14)
node verif36.js ../index.html              # bilan hebdo, statuts d'objectifs, Préparer le call (13)
node verif37.js ../index.html              # tableau de bord, fiche, Mes clients en cartes (15)
```
Attendu sur la v37 : 0 erreur, 19 + 13 + 14 + 13 + 15 vérifications réussies. Le dossier `captures/` est un résultat : ne pas le versionner.

## Ajouter un test pour une nouvelle version
Copier `verif37.js` en `verifNN.js`, garder la simulation Supabase telle quelle, ajouter les vérifications de la phase (présence des éléments, écritures attendues sur les bonnes clés `donnees`, aucune écriture inattendue). Enrichir `fixtures.js` si une nouvelle clé apparaît (respecter exactement la forme écrite par `index.html`).

## Sans Chromium Playwright : le Chrome de la machine
Si `npx playwright install chromium` n'a pas été fait, le préchargement `chrome-systeme.js` fait tourner tous les scripts avec Google Chrome installé (canal « chrome »), sans toucher aux tests :
```
NODE_OPTIONS="--require ./chrome-systeme.js" node rig.js --html ../index.html --out captures/v38
```

## Règle d'or des simulations
Chaque script intercepte Supabase et **ne doit jamais laisser partir une requête vers la vraie base**. Router par nom d'hôte (`new URL(u).hostname === "localhost"`, `.endsWith(".supabase.co")`), jamais par sous-chaîne de l'URL : les appels d'authentification portent `redirect_to=http://localhost…` et seraient sinon envoyés à la vraie base (incident du 25/09/2026, sans conséquence : inscriptions refusées par Supabase, aucune donnée créée).
